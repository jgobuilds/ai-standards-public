# Generated artifacts (house lens)

Anything produced by a build — rendered sites, indexes, architecture diagrams,
compiled docs, assembled deploy trees — is a **derivative**, and the failure mode
is always the same: the derivative and its source drift apart, and nobody notices
because both look fine.

The rule: **a generated artifact must be reproducible from its source, obviously
marked as generated, and gated so drift fails loudly.**

## The failure this exists to prevent

A published reference site was assembled by unpacking a committed zip. The zip
had been produced from the same sources months earlier and then quietly diverged:
it was missing an entire section, a template, and fifteen files' worth of edits,
while holding the **only** copy of the build script that could have regenerated
it. Everything ran. Every check passed. The published output had simply been
wrong for months.

Nothing in that story is exotic. A binary snapshot beside its own sources is a
clock that only ticks in one direction.

## Rules

**1. Regenerate in the build, never ship a snapshot.**
If the deploy consumes a pre-built blob, the blob will go stale. Run the
generator as a build step so the output cannot be older than its input. This also
deletes a whole class of "why does production differ" investigations.

**2. Mark generated files, in the file.**
A header line — *"generated by `<script>` — edit `<source>` instead"* — costs
nothing and is the only thing standing between a well-meaning edit and silent
overwrite. Say it in the repo's instruction file too; both get read at different
moments.

**3. Never hand-edit the output. Fix the generator or the source.**
A hand-edit to a generated file is a change with a delete scheduled for the next
build. If the output is wrong and the source is right, the generator is the bug.

**4. Gate drift in CI.**
Regenerate, then fail if the working tree changed:

```bash
python tools/build.py .
git diff --quiet -- <generated-paths> || { git diff --stat -- <generated-paths>; exit 1; }
```

Without this, committed output silently diverges from committed source and the
repo carries two contradictory truths.

**5. Decide deliberately whether the output is committed at all.**
Both are defensible; the failure is not choosing.

| | Commit the output | Ignore it |
|---|---|---|
| Good when | it is browsed in-repo, or the consumer cannot run the generator | it is a pure deploy artifact |
| Cost | diff noise on every build; needs rule 4 | must be built before it can be inspected |

Commit it *or* ignore it. An output that is sometimes committed is the worst
option, because staleness becomes indistinguishable from "not built yet".

**6. Generated ≠ authored, when reading `git status`.**
Regenerated files appear as modifications and look like someone's work in
progress. Before treating a dirty file as authored content, check whether a
generator owns it — and see `change-safety.md` on staging explicitly, because
this is a common way unrelated changes ride into a commit.

## Line endings, briefly

A generator that writes platform-default endings produces a diff on every run on
a mixed-OS team, which makes rule 4 useless — real drift hides inside noise.
Write output with explicit `\n`, and set `.gitattributes` so the repo agrees with
itself.

## What to check in review

- Can I regenerate this and get a byte-identical result?
- Does the file say it is generated?
- Does CI fail if it drifts?
- Is it committed-or-ignored on purpose, and does the repo say which?
- Does the generator live in the same repo as its output? (A build script that
  exists only inside its own output is the trap described above.)
